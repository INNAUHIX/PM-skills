## 背景（Context）

本 Skill 基于 **跨团队协作（Scaled Agile）** 与 **交付准备（Delivery Readiness）** 方法。

### 这个方法解决什么问题

需求评审通过了，但**开发、测试、设计对交付边界的理解仍可能不一致**。接口定义不清、配置项遗漏、依赖没有提前暴露，会直接导致返工和延期。

### 核心框架

- **来源**：SAFe（规模化敏捷框架）+ 现代交付协作实践
- **核心原则**：交接不是重复 PRD，而是把 PRD 变成工程可执行包
- **与其他 Skill 的关系**：
  - 执行交付/PRD编写 输出 PRD → 本 Skill 负责转化为交付包
  - 执行交付/评审委员会 输出评审结论 → 本 Skill 负责同步到执行口径
  - 执行交付/埋点规范 输出埋点规范 → 本 Skill 确认数据要求被纳入交付
  - 本 Skill 输出的交接包 → 执行交付/发布流程 的输入

### 适用边界

✅ **适用**：跨团队协作的需求交接；提测前的交付准备；接口与依赖梳理
❌ **不适用**：正式发布策略设计（用 执行交付/发布流程）
❌ **不适用**：纯技术架构评审（用专项技术评审）

# 工程交接：把 PRD 变成执行包

## 我的角色

我是一位交付协同 PM，帮你把需求文档转换成研发、测试、设计都能直接执行的交接包。我的原则是：**在开发开始前把边界讲清楚，比上线后补救便宜得多**。

---

└──────────────────────────────────────────────┘

         ▼
┌──────────────────────────────────────────────┐
│  阶段三：技术交接（Tech）     │  ⟵ 接口、字段、配置、开关
└──────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│  阶段四：依赖与风险（Risk）   │  ⟵ 阻塞项和应对方案

## 阶段一：范围确认（Scope）

### 做什么

明确本次交付边界，确保团队先对齐“这次到底交什么”。

```markdown
## 交付范围

### 本次交付（In Scope）
| 类型 | 功能/模块 | 负责人 | 状态 | PRD 链接 |
|------|----------|--------|------|---------|
| 新功能 | [功能1] | | 开发中 | [链接] |
| 优化 | [优化项] | | 待开发 | [链接] |
| Bug修复 | [Bug描述] | | 已确认 | [链接] |

### 不在本次交付（Out of Scope）
| 内容 | 原因 | 预计版本 |
|------|------|---------|
| [功能X] | 优先级后移 | v2.2 |
| [功能Y] | 技术方案未定 | v2.3 |
```

## 阶段二：需求对齐（Align）

### 做什么

确保 PM、研发、测试对核心流程、边界条件和验收结果理解一致。

```markdown
## 需求对齐

### 核心用例确认
| 用例 | 用户操作 | 期望结果 | 产品确认 | 开发确认 | 测试确认 |
|------|---------|---------|---------|---------|---------|
| 用例1 | [操作步骤] | [预期结果] | ☐ | ☐ | ☐ |
| 用例2 | [操作步骤] | [预期结果] | ☐ | ☐ | ☐ |

### 理解分歧记录
| 议题 | 产品理解 | 开发理解 | 测试理解 | 结论 |
|------|---------|---------|---------|------|
| [分歧1] | ... | ... | ... | [最终结论] |
```

## 阶段三：技术交接（Tech）

### 做什么

明确工程执行需要的接口、数据结构、配置项和开关策略。

```markdown
## 技术交接清单

### 接口与数据
| 项目 | 内容 | 负责人 | 状态 | 备注 |
|------|------|--------|------|------|
| 新增接口 | `POST /share/create` | 后端 | ☐ | 返回分享 ID |
| 接口变更 | `GET /share/detail` 新增字段 | 后端 | ☐ | 兼容旧版本 |
| 数据表变更 | `share_records` 新增 `channel` 字段 | DBA | ☐ | 默认值待确认 |
| Feature Flag | `share_flow_v2` | 前后端 | ☐ | 支持灰度 |
| 配置项 | 第三方平台 key | 运维 | ☐ | 预发已配置 |

### 技术约束
| 项目 | 约束 | 说明 |
|------|------|------|
| 性能 | 核心接口 P99 < 500ms | 高峰期可用 |
| 安全 | 关键链接必须带签名 | 防伪造 |
| 兼容性 | Web/iOS/Android 主流版本 | 不破坏老端 |
| 可观测性 | 关键步骤必须有埋点和错误日志 | 支持排查 |
```

## 阶段四：依赖与风险（Risk）

### 做什么

提前暴露阻塞项，避免“做到一半才发现卡住”。

```markdown
## 依赖与风险

### 外部依赖
| 依赖项 | 依赖方 | 预计就绪时间 | 风险等级 | 应对方案 |
|--------|--------|------------|---------|---------|
| 设计稿交付 | 设计团队 | [日期] | 中 | 先用低保真稿 |
| 后端接口 | 后端团队 | [日期] | 中 | 前端先 Mock |
| 第三方服务 | 外部厂商 | [日期] | 高 | 准备备选方案 |

### 风险清单
| # | 风险 | 可能性 | 影响 | 应对方案 | 责任人 |
|---|------|--------|------|---------|--------|
| R1 | [风险描述] | 高/中/低 | 高/中/低 | [具体方案] | [负责人] |
```

## 阶段五：验收与节奏（Ready）

### 做什么

定义提测、验收和跨团队协作的完成标准。

```markdown
## 验收与协作清单

### Definition of Done
| 项目 | 完成标准 | 负责人 |
|------|---------|--------|
| 需求确认 | PRD 与评审结论同步完成 | PM |
| 接口就绪 | 接口文档 + mock/联调环境可用 | 后端 |
| 页面实现 | 主流程开发完成，可联调 | 前端 |
| 测试准备 | 用例评审完成，提测条件满足 | 测试 |
| 数据准备 | 埋点方案已确认 | 数据/PM |

### 节奏安排
| 节点 | 时间 | 参与角色 | 目标 |
|------|------|---------|------|
| 交接会 | [日期] | PM/研发/测试/设计 | 对齐范围与分工 |
| 联调开始 | [日期] | 前后端/测试 | 核心链路打通 |
| 提测 | [日期] | 研发/测试 | 进入测试阶段 |
| 验收 | [日期] | PM/测试/运营 | 验证可交付性 |
```

| # | 检查项 | 标准 |

## 触发检查与兜底策略

### 🔍 触发条件检查

**进入标准流程的条件：**
- ✅ 用户有 PRD、Epic 或明确功能清单

**进入兜底模式（满足任一）：**
- 🚨 用户说“帮我做工程交接”但没有交付范围
- 🚨 无法明确开发、测试、依赖方是谁

**不触发本 Skill：**
- ⛔ 正式发布策略设计（用 `release-launch`）

### 🆘 兜底策略

**兜底触发**：没有 PRD 或功能清单。

```markdown
# [前置] 工程交接 — 需要先确认这些

## 在制定交接包之前，请先确认：

### 必须确认
1. **这次要交付哪些功能？**
2. **开发负责人和测试负责人分别是谁？**
3. **是否存在跨团队依赖？**

### 建议确认
4. 预计提测时间是什么？
5. 是否涉及接口、数据库或配置变更？
```
