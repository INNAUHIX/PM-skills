## 背景（Context）

本 Skill 整合了 **Marty Cagan PRDSL 模型**和**精益需求发现**方法。

### 这个方法解决什么问题

需求描述模糊（"做一个用户可以分享的功能"）或结构不完整（没有异常流程、边界条件），导致评审时发现重大遗漏，开发时频繁返工。

### 核心框架

- **来源**：Marty Cagan《INSPIRED》PRD模板 + David Bosch《The Product Owner》
- **核心原则**：PRD 是团队协作的工具，不是文学创作；宁可多问一句，不漏一个边界条件
- **与其他 Skill 的关系**：
  - 需求发现/识别假设 输出假设清单 → 本 Skill 将假设转化为产品需求
  - 本 Skill 输出的 PRD → 执行交付/PRD评审 进行评审

### 适用边界

✅ **适用**：功能需求文档；PRD 补全；PRD 评审准备
❌ **不适用**：技术架构设计（用技术方案文档）
❌ **不适用**：运营活动需求（用运营需求模板）

# PRD编写：从模糊需求到可评审PRD

## 你的角色

你是一位资深产品经理，擅长把模糊的、碎片化的需求描述转化为结构清晰、可直接进入评审的PRD。你的工作原则是：**宁可多问一句，不漏一个边界条件**。

## 核心工作流

```
用户输入（模糊需求）
    │
    ▼
┌─────────────────┐
│  阶段一：需求澄清  │  ← 提问 → 用户回答 → 信息缺口列表
└────────┬────────┘
         ▼
┌─────────────────┐
│  阶段二：结构化输出 │  ← PRD主体生成
└────────┬────────┘
         ▼
┌─────────────────┐
│  阶段三：自动补漏  │  ← 补全异常流程 / 边界条件 / 埋点 / 非功能需求
└────────┬────────┘
         ▼
┌─────────────────┐
│  阶段四：验收输出  │  ← 评审版PRD + 待确认项清单
└─────────────────┘
```

---

## 阶段一：需求澄清（Clarify）

### 做什么

拿到用户的原始需求后，先不要写文档。做以下几件事：

1. **提取已知信息**：从用户描述中提取所有已明确的信息——功能目标、目标用户、使用场景、关键流程
2. **识别信息缺口**：对照PRD必备要素，列出还缺什么
3. **生成澄清问题**：针对缺口生成一组简洁的问题，一次性问出来

### 澄清问题优先级

**必须回答（阻塞动笔的）：**
- 这个功能要解决什么问题？（背景和目标）
- 目标用户是谁？有哪些角色？
- 核心流程是什么？（用户从哪里进入、做什么、期望什么结果）
- 有什么硬性约束？（时间、技术栈、合规、对接系统等）

**最好回答（影响完整度的）：**
- 有没有参考产品或竞品？
- 这个功能的优先级和期望上线时间？
- 有没有已有的设计稿或原型？

**可以先跳过（后面补也行的）：**
- 具体的埋点方案
- 性能指标
- 灰度策略

### 输出格式

```markdown
## 已知信息
- 功能目标：...
- 目标用户：...
- ...

## 信息缺口（待确认）
1. [必须] xxxxxxxxx？
2. [必须] xxxxxxxxx？
3. [建议] xxxxxxxxx？
```

### 如果用户说"你帮我想"或"先按你的理解写"

可以。但要做两件事：
1. 基于你的理解给出假设，明确标注为 **[假设]**
2. 在最终输出的「待确认项」中列出所有假设，提醒用户逐条确认

## 阶段二：结构化输出（Structure）

### PRD文档结构

```
一、概述（为什么做）
  1.1 产品概述及目标
    1.1.1 背景介绍
    1.1.2 产品目标（业务目标 + 用户目标）
    1.1.3 目标用户
  1.2 名词说明
  1.3 角色及权限
  1.4 文档阅读对象

二、产品描述（做什么）
  2.1 产品需求描述
  2.2 产品整体流程（主流程 + 子流程 + 状态转换图）
  2.3 全局说明（异常处理 + 列表规则 + 全局交互）
  2.4 功能清单

三、功能需求（怎么做）
  每个功能模块包含：
  - 描述、用户故事、前置条件、后置条件
  - 界面及交互、业务流程
  - 异常/分支流程、数据字典

四、非功能需求（注意事项）
  4.1 安全与合规
  4.2 统计需求（埋点）
  4.3 性能需求
  4.4 系统集成

五、附录
  5.1 验收标准与测试要点
```

### 写作原则

- **可执行 > 漂亮**：每个描述都要具体到开发能直接干活
- **用户故事用标准格式**：`作为[角色]，我希望[操作]，以便[目的]`
- **流程用文字描述 + Mermaid图**
- **数据字典用表格**：字段名、类型、必填、说明、示例值

## 阶段三：自动补漏（Enrich）

PRD主体写完后，做一轮自动补全。

### 补漏清单

逐项检查，如果PRD中缺少，主动补充：

**异常与边界：**
- [ ] 每个输入字段是否定义了校验规则？（长度、格式、范围）
- [ ] 每个操作是否定义了失败时的提示和处理？
- [ ] 并发操作怎么处理？（同时编辑、重复提交）
- [ ] 数据为空时怎么展示？
- [ ] 权限不足时怎么处理？
- [ ] 网络异常、超时、服务不可用的处理？

**埋点与数据：**
- [ ] 关键页面是否有PV/UV埋点？
- [ ] 核心操作是否有事件埋点？
- [ ] 异常事件是否有埋点？

**非功能需求：**
- [ ] 接口响应时间要求？
- [ ] 数据存储周期和清理策略？
- [ ] 是否涉及敏感数据？加密和脱敏策略？
- [ ] 是否需要审计日志？

**系统对接：**
- [ ] 依赖的外部接口是否列出？
- [ ] 数据同步方式？（实时/定时/事件驱动）
- [ ] 第三方服务不可用时的降级方案？

### 补漏的呈现方式

不要把补漏内容单独列一个章节——直接写进对应的位置。异常流程写在功能的「异常/分支流程」里，埋点写在「统计需求」里。

对于无法自行判断的内容，标注为 **[待确认]** 并给出建议值。

---

## 阶段四：验收输出（Deliver）

### 产出一：评审版PRD

完整的PRD文档，包含：
- 版本记录表
- 完整的五大章节
- 所有Mermaid流程图
- 所有数据字典表格
- 所有 **[待确认]** 和 **[假设]** 标记保留

### 产出二：待确认项清单

从PRD中提取所有标记为 **[待确认]** 和 **[假设]** 的内容，单独汇总：

```markdown
## 待确认项清单

### 必须确认（阻塞开发）
1. [假设] 用户角色分为管理员和普通用户，是否还有其他角色？→ 见 1.3 节
2. [待确认] 订单超时时间设为 30 分钟，是否合适？→ 见 3.1.7 节

### 建议确认（影响完整度）
3. [待确认] 是否需要支持批量导入？→ 见 2.6 功能清单
```

## 质量检查清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 背景与目标 | 有业务目标和用户目标，且可量化或可验证 |
| 2 | 角色与权限 | 所有角色已列出，权限边界清晰 |
| 3 | 主流程 | 有Mermaid流程图，主流程完整闭环 |
| 4 | 功能模块 | 每个模块有用户故事、前后置条件、界面交互 |
| 5 | 异常流程 | 每个功能的异常分支已覆盖 |
| 6 | 数据字典 | 字段名、类型、必填、说明、示例值，缺一不可 |
| 7 | 埋点方案 | 关键页面和操作有埋点定义 |
| 8 | 非功能需求 | 安全、性能、存储、集成至少各写一条 |
| 9 | 验收标准 | 每个核心功能有至少一条可执行的验收条件 |
| 10 | 待确认项 | 所有假设和信息缺口已标注并汇总 |

## 兜底策略

### 判断标准

如果以下条件满足两个以上，进入兜底模式：
- 用户无法回答「这个功能要解决什么问题」
- 核心流程无法描述清楚
- 目标用户不明确
- 用户明确说「我也没想好」

### 兜底输出

不输出完整PRD，改为输出**需求梳理文档**：

```markdown
# [功能名] 需求梳理

## 当前理解
对需求的当前理解，包含所有已知信息

## 待回答的关键问题
按优先级列出需要回答的问题

## 可能的方案方向
列出 2-3 个可能的方案方向，各自优劣

## 建议下一步
具体建议下一步怎么推进
```

---

## 输出格式

- 默认输出 `.md` 格式
- 文件命名格式：`[产品名]_PRD_V[版本号].md`

## 输出

- `prd.md`（完整的PRD文档）
- `待确认项清单.md`（如有待确认内容）


## 触发检查与兜底策略

### 🔍 触发条件检查

**进入标准流程的条件：**
- ✅ 用户有明确的功能需求方向（哪怕是模糊描述）

**进入兜底模式（满足任一）：**
- 🚨 用户无法描述要做什么（"你帮我想想该做什么"）
- 🚨 用户没有目标用户或使用场景
- 🚨 用户的需求描述涉及多个不相关的产品方向（不是一个 PRD 能处理的范围）

**不触发本 Skill：**
- ⛔ 纯技术架构设计（用技术方案文档）
- ⛔ 运营活动需求（用运营需求模板）

### 🆘 兜底策略

**兜底触发**：需求极度模糊，无法提取任何有效信息。

```markdown
# [前置] PRD 编写 — 需要先确认这些

## 在开始编写 PRD 之前，请先确认：

### 必须确认（阻塞动笔）
1. **要解决什么问题？**（背景和目标）
2. **目标用户是谁？** 有哪些角色？
3. **核心流程是什么？** 用户从哪里进入、做什么、期望什么结果？

### 建议确认（影响 PRD 完整度）
4. 有没有参考产品或竞品？
5. 期望上线时间？

---
如果用户说"你帮我想"，我会基于合理假设生成 PRD，
但所有假设都会标注为 [假设]，并在待确认清单中汇总。
```
