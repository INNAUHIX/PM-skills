## 背景（Context）

本 Skill 基于 **持续交付（CD）最佳实践**和**精益发布策略**。

### 这个方法解决什么问题

功能开发完了，但**发布时出问题**（数据库没同步、配置没改，回滚方案没准备）是团队最常见的低级失误。本 Skill 让发布前有检查、发布时有节奏、发布后有监控。

### 核心框架

- **来源**：Jez Humble《持续交付》+ Nicole Forsgren《Accelerate》
- **核心原则**：发布是开始，不是结束；灰度优于全量，回滚先于修复
- **与其他 Skill 的关系**：
  - 产品规划/路线图规划 输出版本计划 → 本 Skill 负责发布执行
  - 本 Skill 输出的发布检查清单 → 执行交付/复盘学习 的输入之一

### 适用边界

✅ **适用**：新功能发布；重大版本更新；灰度发布策略设计
❌ **不适用**：每日 Bugfix 小更新（简化检查清单即可）
❌ **不适用**：基础设施变更（需要独立的变更管理流程）

# release-launch：版本发布全流程

## 我的角色

我是一位项目管理专家，帮你把"功能开发完了"变成"用户用上了且没出问题"。我的原则是：**发布是开始，不是结束——发布前充分的准备，才能让发布后从容不迫**。

## 步骤二：灰度策略设计

### 灰度策略选择

| 策略 | 适用场景 | 风险 | 推荐程度 |
|------|---------|------|---------|
| **全量发布** | Bugfix、低风险优化、内部工具 | 高（问题直接影响所有用户）| 仅限低风险改动 |
| **百分比灰度** | 新功能、重大改版 | 中 | 首选 |
| **白名单灰度** | 高价值用户、VIP 用户先跑 | 中 | 有明确高价值用户群时 |
| **定向灰度** | 特定地区/渠道/版本 | 低 | 有限定条件时优先 |
| **开关灰度** | 功能可配置，可热开启 | 低 | 推荐，可随时回滚 |

### 百分比灰度方案模板

```markdown
## 灰度发布方案

### 阶段一：内部验证（Day 0）
- 范围：仅内部员工账号（约 {{N}} 人）
- 开启条件：所有内部测试通过
- 验证内容：
  - [ ] 核心功能可正常操作
  - [ ] 监控指标无异常
  - [ ] 日志无错误
- 通过标准：24 小时内无 P0 问题

### 阶段二：小范围灰度（Day 1-2）
- 范围：5% 用户（约 {{N}} 用户）
- 开启条件：内部验证通过
- 验证内容：
  - [ ] 核心指标无明显下降
  - [ ] 错误率无上升
  - [ ] 客服反馈无集中投诉
- 通过标准：48 小时内无 P0/P1 问题

### 阶段三：扩大灰度（Day 3-5）
- 范围：20% → 50% → 100%（逐步扩量）
- 每步扩量后观察 2-4 小时
- 触发回滚条件：
  - 错误率上升超过 0.5%
  - 核心功能转化率下降超过 5%
  - 客服投诉集中爆发

### 阶段四：全量发布（Day 5+）
- 确认无问题后全量
- 全量后保留灰度开关 48 小时（热回滚能力）
```

### 灰度发布风险评估

```markdown
## 灰度风险评估

| 功能 | 风险等级 | 影响用户范围 | 回滚难度 | 应对措施 |
|------|---------|------------|---------|---------|
| XX 新功能 | 🟡 中 | 中 | 低（有开关）| 开关灰度，关闭即恢复 |
| YY 支付改版 | 🔴 高 | 广 | 高（数据已落库）| 白名单先行，准备数据回滚脚本 |
| ZZ Bugfix | 🟢 低 | 小 | 低 | 全量发布 |
```

## 步骤六：回滚方案

### 回滚触发条件（任一满足立即回滚）

```markdown
## 回滚触发条件

| 条件 | 阈值 | 监控指标 |
|------|------|---------|
| 核心功能不可用 | 错误率 > 5% | 监控系统 |
| 错误日志突增 | 5 分钟内 ERROR 日志 > 100 条 | 日志平台 |
| 服务崩溃 | Pod 重启 > 3 次 | K8s 监控 |
| 数据异常 | 业务数据出现脏数据 | 数据监控 |
| 客服集中投诉 | 5 分钟内同类投诉 > 10 条 | 客服系统 |
```

### 回滚操作手册

```markdown
## 回滚操作手册

### 自动回滚（推荐）
- K8s Rollback：自动回滚到上一稳定版本
- Feature Flag 回滚：关闭开关即可（热回滚，推荐）

### 手动回滚（如需）
1. 停止发布进程
2. 执行回滚脚本：`./rollback.sh {{VERSION}}`
3. 确认服务恢复正常
4. 通知发布群：已回滚 + 原因
5. 保留现场，开始排查

### 回滚决策人
发布出现问题时，由 **值班技术负责人** 决定是否回滚。
授权规则：值班人员有权先回滚再汇报。
```

## 步骤七：发布后监控

### 黄金监控期

发布后 24-48 小时是问题高发期，需要密集监控：

```markdown
## 发布后监控计划

### 发布后 0-2 小时（密集监控）
| 指标 | 正常范围 | 告警阈值 | 负责人 |
|------|---------|---------|--------|
| 服务错误率 | < 0.1% | > 0.5% | @值班研发 |
| 服务响应时间 P99 | < 500ms | > 1000ms | @值班研发 |
| 核心功能成功率 | > 99% | < 98% | @值班研发 |
| 数据库慢查询 | < 10 QPS | > 50 QPS | @值班 DBA |

### 发布后 24 小时（常规监控）
| 指标 | 关注内容 |
|------|---------|
| 用户反馈 | 客服投诉数量和内容 |
| 业务数据 | 新功能使用率是否符合预期 |
| 资源消耗 | CPU/内存/磁盘有无异常增长 |

### 发布后 48 小时
- [ ] 指标回归正常基线
- [ ] 无新增问题
- [ ] 发布总结邮件发送
```

## 兜底策略

### 发布过程中出现问题

1. **立即通知发布群**（不是等修好再通知）
2. **按回滚触发条件判断是否回滚**（不要等，不要犹豫）
3. **回滚优先，保护用户**（修好再重新发布）
4. **保留现场**（日志、监控截图、错误信息）
5. **48 小时内输出事故报告**

### 灰度过程中发现严重问题

- 立即停止扩量
- 已灰度用户回滚（如有必要）
- 立即通知 PM 和运营
- 评估是修后重新灰度还是取消发布

## 触发检查与兜底策略

### 🔍 触发条件检查

**进入标准流程的条件：**
- ✅ 用户有明确的功能清单和上线时间

**进入兜底模式（满足任一）：**
- 🚨 用户说"帮我制定发布计划"但没有功能清单
- 🚨 上线时间不明确

**不触发本 Skill：**
- ⛔ 纯 Bugfix 小更新（用简化的发布检查清单即可）

### 🆘 兜底策略

**兜底触发**：没有功能清单或上线时间。

```markdown
# [前置] 发布计划 — 需要先确认这些

## 在制定发布计划之前，请先确认：

### 必须确认
1. **发布内容**：这次发布包括哪些功能/Bugfix？
2. **上线时间**：计划什么时间发布？
3. **团队信息**：谁负责发布？谁负责回滚？

### 建议确认
4. 这次发布是否涉及数据库变更？
5. 有没有灰度要求？（全量/白名单/百分比）

---
如果信息不足，我会输出一份通用的发布计划模板，
用户根据实际情况填充。
```
