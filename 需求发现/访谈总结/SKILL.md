## 背景（Context）

本 Skill 融合了 **Jobs-to-be-Done（JTBD）** 框架与结构化访谈分析方法。

### 这个方法解决什么问题

用户访谈结束后，团队通常有一份录音或文字记录，但**缺乏系统的方法从中提取可行动的产品洞察**。很多团队访谈完了也不知道"用户真正想要什么"。

### 核心框架

- **来源**：Jonah Gorlin《Validating Product Ideas》+ Jeff Gothelf《Sense and Respond》
- **关键原则**：每个洞察必须有原始记录支撑，不能靠揣测
- **与其他 Skill 的关系**：
  - 需求发现/访谈提纲 负责设计访谈问题 → 输出访谈记录
  - 本 Skill 负责从记录中提炼洞察 → 输出洞察清单
  - 洞察清单 → 输入到 需求发现/识别假设 转化为产品假设

### 适用边界

✅ **适用**：访谈录音/文字记录的结构化提炼；多份访谈的交叉模式发现
❌ **不适用**：问卷数据的分析（问卷数据用 需求发现/识别假设）
❌ **不适用**：竞品用户访谈记录（竞品分析用 产品规划/竞品简报）

# 访谈总结：从原始记录到结构化洞察

## 我的角色

我是一位用户研究员，擅长从零散的访谈记录中提炼出清晰的产品洞察。我的原则是：**每一句总结都要能追溯到原始记录，绝不凭空捏造**。

## 我的工作流

```
用户输入（访谈记录 / 访谈目标 / 产品背景）
    │
    ▼
┌──────────────────────────────────────────────┐
│  阶段一：阅读理解         │  ⟵ 通读全文、标记要点
│  这份访谈讲了什么？                            │
└──────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│  阶段二：提取洞察          │  ⟵ 关键发现、模式识别
│  用户的核心诉求是什么？                        │
└──────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────┐
│  阶段三：生成假设          │  ⟵ 将洞察转化为可验证假设
│  这些洞察意味着什么？                          │
└──────────────────────────────────────────────┘
         │
         ▼
    输出总结报告
```

---

## 阶段一：阅读理解（Reading）

### 做什么

通读访谈记录，标记关键信息：

1. **事实信息**：用户说的具体行为、场景、工具
2. **情感信号**：用户表达的情绪、痛点、期待
3. **矛盾点**：用户说法前后不一致的地方
4. **金句**：用户说的有代表性的原话

### 输出格式

```markdown
## 访谈基本信息
- 受访者：[用户画像]
- 时间：[访谈日期]
- 时长：[分钟]
- 访谈目标：[验证什么]

## 关键片段标注
| 时间点 | 类型 | 内容摘要 | 原话 |
|--------|------|---------|------|
| 05:23 | 痛点 | 手动导出数据很麻烦 | "每次都要点三次才能导出" |
| 12:45 | 需求 | 希望能一键导出 | "如果有快捷键就好了" |
```

---

## 阶段二：提取洞察（Insight）

### 洞察类型

| 类型 | 定义 | 示例 |
|------|------|------|
| **痛点** | 用户表达的困难或不满 | 导出流程繁琐 |
| **需求** | 用户期待的功能或体验 | 一键导出功能 |
| **行为** | 用户实际做的事 | 用截图保存数据 |
| **动机** | 行为背后的原因 | 担心数据丢失 |
| **场景** | 具体的使用环境 | 月底汇报时 |

### 洞察模板

```markdown
## 洞察清单

### 洞察 1：[标题]
- 类型：痛点/需求/行为/动机/场景
- 内容：[一句话描述]
- 证据：[引用原话，注明时间点]
- 影响用户数估计：[单个/部分/多数]
```

---

## 阶段三：生成假设（Hypothesis）

将洞察转化为可验证的产品假设：

```markdown
## 待验证假设

| ID | 假设 | 来源洞察 | 验证方法 | 优先级 |
|----|------|---------|---------|--------|
| H1 | 用户需要一键导出功能 | 洞察1 | 原型测试 | 高 |
| H2 | 导出功能能提升留存 | 洞察1+洞察3 | 数据分析 | 中 |
```

---

## 输出检查清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 每个洞察都有原话支撑 | 引用具体内容 |
| 2 | 洞察分类正确 | 痛点/需求/行为/动机/场景 |
| 3 | 假设可验证 | 具体、可测试 |
| 4 | 无主观臆断 | 区分用户说的 vs 我推断的 |

---

## 输出格式

- 默认输出 `.md` 格式
- 文件命名格式：`interview_summary_[受访者]_[日期].md`



## 🤖 AI 协作模式

### 自动提炼洞察

AI 可从访谈记录中自动提取洞察：

**输入：** 访谈记录文字稿
**输出：** 洞察清单 + 新假设

**示例：**
```
输入（访谈记录）：
"周报大概要花 1 小时，主要是回忆这周做了什么。方案文档更头疼，
有时候半天写不完。用 ChatGPT 写过邮件，感觉不错但不太懂我们
公司的业务语境。如果月费 29 元，我会试。"

AI 自动输出：

## 洞察提炼

| 类型 | 内容 | 证据 | 影响用户数 |
|------|------|------|-----------|
| 痛点 | 周报/方案写作耗时过长 | "1小时"、"半天写不完" | 多数 |
| 痛点 | 通用AI不懂业务语境 | "不太懂公司业务语境" | 多数 |
| 需求 | 需要贴合业务场景的AI写作 | "得真的有用" | 多数 |
| 动机 | 愿意为有效工具付费 | "月费29元会试" | 部分 |

## 新假设

| ID | 假设 | 来源 | 优先级 |
|----|------|------|--------|
| H8 | 通用AI写作工具"不够用"是核心痛点 | 洞察1+2 | 高 |
| H9 | "懂业务语境"是比"写得快"更重要的差异化 | 洞察2 | 高 |
```

## 📦 数据接口

### 输入格式

```json
{
  "interview_records": [
    {
      "respondent": "受访者标识",
      "content": "访谈记录文字稿"
    }
  ],
  "interview_script": {...}
}
```

### 输出格式（可循环回 identify-needs）

```json
{
  "insights": [
    {
      "type": "痛点|需求|行为|动机|场景",
      "content": "洞察内容",
      "evidence": "证据（原话）",
      "impact": "单个|部分|多数"
    }
  ],
  "new_hypotheses": [
    {
      "id": "H8",
      "content": "假设内容",
      "source_insights": ["洞察1", "洞察2"],
      "priority": "高|中|低"
    }
  ],
  "should_loop": true
}
```

### 循环机制

当 `should_loop: true` 时，新假设应传递回 `identify-needs` Skill，
形成发现循环：识别假设 → 排优先级 → 访谈 → 提炼洞察 → 新假设

## 触发检查与兜底策略

### 🔍 触发条件检查

**进入标准流程的条件：**
- ✅ 用户提供了访谈记录（录音转文字 / 文字记录 / 会议纪要）

**进入兜底模式（满足任一）：**
- 🚨 用户说"帮我总结"但没有提供任何访谈记录
- 🚨 提供的记录极度简短（少于 5 句话），无法提炼洞察
- 🚨 用户提供了多个人的名字列表而非访谈内容

**不触发本 Skill：**
- ⛔ 用户上传的是问卷数据（用 需求发现/识别假设）
- ⛔ 用户要分析的是竞品资料（用 产品规划/竞品简报）

### 🆘 兜底策略

**兜底触发**：没有访谈记录，或记录内容不足以提炼洞察。

```markdown
# [前置] 访谈总结 — 需要先确认这些

## 在生成总结报告之前，请提供以下信息：

### 必须提供
1. **访谈记录**：访谈的原始文字记录或录音转文字内容
2. **受访者背景**：受访者是谁？（用户画像/职业/使用场景）
3. **访谈目标**：这次访谈主要想验证/了解什么？

### 建议提供
4. 访谈时长
5. 有没有录音可以提供文字版？

---
如果只有几句话的简短记录，我会基于现有内容生成初步洞察，
但请注意：样本量太小，结论的可靠性有限。
```
## Skill 协同

### 上游 Skill（输入来源）
| Skill | 输出内容 | 如何配合 |
|-------|---------|---------|
| 需求发现/访谈脚本 | 访谈脚本 | 访谈结束后，对记录进行总结 |
| 用户直接提供 | 访谈记录文字稿 | 直接提炼洞察 |

### 下游 Skill（输出去向）
| Skill | 接收内容 | 如何配合 |
|-------|---------|---------|
| 需求发现/识别假设 | 洞察清单 + 待验证假设 | 将洞察转化为可验证的产品假设 |
| 需求发现/优先级排序 | 洞察驱动的假设 | 对假设排优先级 |

### 推荐的 Commands
- `/discover` 需求发现流程中，访谈完成后自动调用
- `/interview` 访谈流程中的 `summarize` 子命令

```
需求发现阶段
  访谈脚本 -> [访谈记录] -> 访谈总结 -> [洞察清单]
                                    -> 识别假设 (新假设)
```
