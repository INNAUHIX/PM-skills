## 背景（Context）

本 Skill 基于 **User Story Mapping** 与 **MVP Slice** 的产品拆解方法。

### 这个方法解决什么问题

路线图里有 Epic，PRD 也会写，但团队常常不知道**中间那层产品结构该怎么拆**。结果要么一次写太大，做成“大而全”；要么直接拆成技术任务，失去用户视角。用户故事地图可以把“战略目标”翻译成“可交付的用户价值切片”。

### 核心框架

- **来源**：Jeff Patton《User Story Mapping》+ Lean MVP 切片方法
- **核心原则**：先按用户任务流组织，再做版本切片；MVP 不是最少功能，而是最小可验证价值
- **与其他 Skill 的关系**：
  - 「pm-roadmap-planner」Skill 输出 Epic/版本目标 → 本 Skill 负责拆成故事地图
  - 本 Skill 输出的 MVP 切片 → 「prd-writer」Skill 可据此编写单个 PRD
  - 本 Skill 输出的故事列表 → 「iteration-planning」Skill 可继续排 Sprint

### 适用边界

✅ **适用**：路线图落地、Epic 拆解、MVP 规划、跨团队对齐
❌ **不适用**：纯技术任务拆分（交给研发排期）
❌ **不适用**：单个 UI 页面线框设计（交给原型或设计）

# 用户故事地图：从 Epic 到 MVP 切片

## 我的角色

我是一位产品交付设计师，帮你把高层目标拆成用户能感知、团队能执行的故事地图。我的原则是：**所有拆解都要回到用户任务，而不是从系统模块倒推**。

## 步骤一：定义用户任务流

### 做什么

先从用户完成目标的完整路径出发，定义骨架任务。

```markdown
## 用户任务流

### 用户目标
- [目标用户] 想完成什么？

### Backbone Tasks
1. 发现入口
2. 创建内容
3. 确认设置
4. 执行提交
5. 查看结果
6. 处理异常

---

## 步骤二：拆用户故事

### 做什么

在每个主干任务下面，拆分出可交付的用户故事。

```markdown
## 用户故事清单

| 主干任务 | 用户故事 | 价值说明 | 依赖 | 优先级 |
|---------|---------|---------|------|--------|
| 发现入口 | 作为新用户，我希望在首页看到分享入口 | 让用户知道能力存在 | 首页导航 | 高 |
| 创建内容 | 作为用户，我希望选择要分享的内容 | 完成主流程第一步 | 内容列表 | 高 |
| 确认设置 | 作为用户，我希望选择分享渠道 | 满足不同场景 | 渠道配置 | 中 |
| 查看结果 | 作为用户，我希望看到分享是否成功 | 提供反馈 | 接口返回 | 高 |

---

## 步骤三：切 MVP

### 做什么

找出验证核心价值所需的最小故事集合。

```markdown
## MVP 切片

### 核心假设
- [这次要验证什么价值或行为]

### MVP 必须包含
| 故事 | 为什么必须有 |
|------|-------------|
| [故事1] | 没有它主流程无法成立 |
| [故事2] | 没有它无法验证用户是否完成目标 |

### MVP 暂不包含
| 故事 | 延后原因 |
|------|---------|
| [故事A] | 只提升体验，不影响核心验证 |
| [故事B] | 高成本，先不投入 |

---

## 步骤四：定义版本层次

### 做什么

把用户故事分配到 MVP、V1、V2。

```markdown
## 版本分层

| 版本 | 目标 | 包含故事 | 成功指标 |
|------|------|---------|---------|
| MVP | 验证核心流程能否跑通 | [故事1,2,3] | [激活率/成功率] |
| V1 | 补齐主要使用场景 | [故事4,5] | [转化率/留存] |
| V2 | 做体验优化和扩展能力 | [故事6,7] | [满意度/复用率] |

---

## 步骤五：输出交付清单

```markdown
# [Epic名称] 用户故事地图

## 1. 用户目标与任务流
[任务流]

## 2. 用户故事清单
[故事列表]

## 3. MVP 切片
[MVP 必须/暂不包含]

## 4. 版本分层
[MVP / V1 / V2]

## 5. 下一步建议
- 哪些故事适合先写 PRD
- 哪些故事可直接进入 Sprint 拆解

---

## 输出检查清单

| # | 检查项 | 标准 |
|---|--------|------|
| 1 | 主干任务清晰 | 按用户时间顺序组织 |
| 2 | 用户故事合格 | 从用户视角表达，可独立验收 |
| 3 | MVP 闭环成立 | 最小集合可验证核心价值 |
| 4 | 版本边界明确 | MVP / V1 / V2 不混乱 |
| 5 | 下游可消费 | PRD 和 Sprint 都能直接使用 |

---

## 输出格式

- 默认输出 `.md` 格式
- 文件命名格式：`[Epic名]_用户故事地图_[日期].md`

## 触发检查与兜底策略

### 🔍 触发条件检查

**进入标准流程的条件：**
- ✅ 用户至少提供一个 Epic、目标场景或版本目标

**进入兜底模式（满足任一）：**
- 🚨 用户只说“帮我拆一下”但没有明确产品目标
- 🚨 无法说清目标用户是谁

**不触发本 Skill：**
- ⛔ 纯技术实现拆解

### 🆘 兜底策略

**兜底触发**：没有明确 Epic 或目标用户。

```markdown
# [前置] 用户故事地图 — 需要先确认这些

## 在拆故事之前，请先确认：

### 必须确认
1. **目标用户是谁？**
2. **这次要完成的核心任务是什么？**
3. **本轮最想验证的核心假设是什么？**

### 建议确认
4. 当前已经确定了哪些功能边界？
5. 有没有必须保留的业务约束？

## Skill 协同

### 上游 Skill（输入来源）
| Skill | 输出内容 | 如何配合 |
|-------|---------|---------|
| 「pm-roadmap-planner」 | Epic / 版本目标 | 拆成用户任务流和版本切片 |

| 「iteration-planning」 | 故事清单 / 版本分层 | 继续排 Sprint |
